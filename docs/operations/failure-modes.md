## What the failure tests found (all fixed, with regression tests)

1. **A stopped Redis froze the entire API, including `/health/live`** (first run: every probe timed out for 20+ s). Two causes: (a) redis-py had no timeouts, so any request touching Redis waited for the OS to give up; (b) worse, the cross-process metrics sink flushed to Redis *synchronously on the event loop*, so one unreachable Redis stalled every request in the process. Fixed with socket timeouts (1 s connect / 2 s command), a circuit breaker (after one failure the rest fail instantly for 5 s), a dedicated pub/sub connection, and an off-loop metrics flusher. Re-run: all reads 200 during the outage.
2. **A stopped PostgreSQL produced HTTP 500s and 60-second hangs**: connection errors arrive unwrapped (`ConnectionRefusedError`, `socket.gaierror`), asyncpg waits 60 s to connect, and "database system is shutting down" is a `DBAPIError` that was not recognised as transient. Fixed with a 5 s connect timeout and handlers mapping connection-class errors and transient SQLSTATE classes (08, 40, 53, 57) to 503 + `Retry-After`.
3. **Tasks of a hard-killed worker waited 20 minutes for redelivery** (visibility timeout was 2× a 10-minute limit). Limits are now 240 s soft / 300 s hard and redelivery happens after 6 minutes.
4. **Reads depended on the football provider** (`GET /competitions` 500'd when it was down and consumed quota when Redis was); fixed (S-17).
5. The **WebSocket send loop** serialised on slow clients (S-14).

## Worker kill result

`load/worker_kill.sh` (final build): 60 tasks queued while the worker was stopped; worker started, `SIGKILL`ed 14 s later holding 2 tasks (48 still queued).
After the container was started again: **the 48 queued tasks ran within 74 s**; the 2 tasks that were in flight sat *unacked* and were **redelivered and acknowledged at t = 416 s** (visibility timeout 360 s,
polled every 15 s). Nothing was lost; nothing ran twice that was not safe to (all tasks are idempotent). Before the fix (visibility timeout 2 × 600 s = 20 min) those two tasks would have waited 20 minutes.
If a faster redelivery matters for a particular task, lower `CELERY_TASK_TIME_LIMIT_SECONDS` (the visibility timeout follows: limit + 60 s).
