# Caching strategy

Principle: **the database is the truth, Redis is a short-lived copy of expensive reads, and no cache may make live data older than a user would tolerate.**
Reads are cache-aside (`CacheAside`): try Redis, on a miss compute from Postgres and store with a TTL; any Redis failure is treated as a miss, so a cache outage costs speed, never correctness.
Nothing user-specific is cached except the personalised feed (45 s, keyed by user id). Viewer-specific fields of shared responses (`mine`, `liked_by_me`) are added *after* the cache.

| Data | Where cached | TTL | Invalidated by | If the cache is unavailable | Staleness a user can see |
|---|---|---|---|---|---|
| Live matches, match detail | Redis | **30 s** | deleted by the sync worker on every change; WebSocket pushes the change immediately | straight from Postgres (≤ 30 s behind the provider anyway: that is the poll interval) | ≤ 30 s; clients show `STALE` when the last provider sync is old |
| Today / upcoming fixtures, team & competition pages, standings, squads | Redis | 300 s | sync-time deletes of affected keys (standings on full-time) | Postgres | ≤ 5 min (≈ a poll cycle) |
| Lineups, statistics, form, head-to-head, insights of **finished** matches; player profiles | Redis | 3600 s | TTL (the data no longer changes) | Postgres | none material |
| Same, for a **live** match | Redis | 30 s | sync deletes | Postgres | ≤ 30 s |
| Analytics (team/player/comparison) | Redis | 900 s | TTL; regenerated by beat every 15 min | Postgres (heavier: aggregate queries) | ≤ 15 min — acceptable, labelled analytics not scores |
| Predictions | Redis | 300 s | regenerated every 30 min; evaluated after full-time | Postgres | ≤ 5 min |
| **Unified search** results | Redis | **30 s** (Phase 7) | TTL | Postgres | ≤ 30 s (may include a score) |
| Search suggestions | Redis | 120 s | TTL | Postgres | irrelevant |
| Trending | Redis | 900 s | recomputed every 5 min by beat | stale-free fallback: empty lists | ≤ 15 min |
| News lists, article pages, discovery home | Redis | 120 s | **version bump on any content change** (publish, edit, unpublish, delete) invalidates every key at once | Postgres | none after an edit (instant); ≤ 2 min otherwise |
| Personalised feed | Redis, per user | 45 s | TTL | Postgres | ≤ 45 s |
| Comment pages, reaction/poll counters | Redis | 30 s | bumped on every write, so a new comment shows at once; rebuilt from Postgres if Redis forgets | Postgres | none |
| Subscription / entitlements | **never cached** | — | — | — | none: cancellation and refunds take effect on the next request |
| Auth state (user row, role, suspension) | **never cached** | — | — | — | none |
| Media (images) | CDN / `Cache-Control: immutable` + ETag; delivery metadata in Redis 1 h | 1 y | URL changes with the content | S3 | none |
| Web pages (SSR) | not cached (`force-dynamic`) | — | — | — | none — scores must never be static |
| Mobile board | on-device copy of the last good response, ≤ 24 h, **always labelled as old** | 24 h | replaced on the next successful load | shown with "You're offline. Showing scores saved at 14:02 (3 h ago)" | explicit |

## Rules that keep this safe

1. A cache entry is never longer-lived than the sync that feeds it, for anything that can change during a match.
2. Writes that matter to the reader delete or version-bump the relevant keys in the same step (`_publish_changes`, `ArticleService.bump_version`, comment/reaction writes).
3. Every key family has a TTL — enforced by `test_no_cache_or_counter_key_family_is_written_without_an_expiry` (a scan after a full scenario). The Celery queue and the
   metric counters are the documented exceptions.
4. Cache stampede: a miss recomputes per request (no lock). At the current scale the recompute is a handful of indexed queries; if a very hot key ever needs it, add single-flight there.
5. Redis cannot be a source of authority: nothing in it decides who someone is or what they have paid for.
